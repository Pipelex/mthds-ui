# The run timeline

`RunTimeline` draws a running run's progress the way a workflow engine's event timeline does: one row per invocation of a pipe, nested under the controller that ran it, and a bar on a shared time axis from the invocation's start to its end, which grows while the invocation runs. It draws from the **progress snapshot** of the hosted progress contract and from nothing else: no method graph is drawn beforehand, a row appears only when the run reaches its invocation, and no batch width is ever guessed.

```tsx
import { RunTimeline } from "@pipelex/mthds-ui/timeline/react";
import type { ProgressSnapshot } from "@pipelex/mthds-ui/timeline";

<RunTimeline snapshot={snapshot} theme="dark" />;
```

The component and its stylesheet live behind `./timeline/react`, whose entry imports the stylesheet itself, so a host's bundler picks it up with the component. The snapshot's types, the invocation path grammar and the pure projection the component draws live behind `./timeline`, which needs neither React nor anything else installed, so a server or a worker can read a snapshot with the same code the timeline uses.

## The snapshot, and where it comes from

The snapshot is data, defined apart from the carriers that deliver it: a progress route a client polls, a frame over a WebSocket that tells a browser the snapshot has a newer version, or the state another workflow platform publishes for a task. The timeline reads the snapshot alone, so it draws a run from any carrier and any engine that publishes it. `ProgressSnapshot` and `ProgressInvocation` model it field for field: `pipe_type` and `degradation.reason` are open strings, an optional field is absent rather than `null`, and a member the types do not know is ignored rather than rejected.

**Hand the timeline every snapshot you read.** Reads that overlap can answer out of order, so the timeline keeps, of the snapshot it holds and the one it is handed, the fresher by the contract's rule (`fresherSnapshot`):

- never a snapshot showing the run pending or running over one showing it ended, whatever their versions;
- otherwise the higher `version`;
- at the same version, the later `assembled_at`, compared exactly at every fractional digit the two carry (`compareTimestamps`), never as numbers rounded to what a double holds.

A late answer with a lower version therefore changes nothing, and once the run has ended no snapshot of it still going replaces it. A snapshot of another run, another mode or another part of a run belongs to another stream of progress (`progressStreamKey`), so it is not compared with the held one at all and replaces it outright: a host that switches the timeline to another run must therefore discard the reads still in flight for the run it left, or a late answer for that run will switch the timeline back. A host that wants to rewind, as the stories' replay does, mounts a fresh timeline with a new `key`.

Timestamps are read as the contract writes them, RFC 3339 with an upper-case `T` and either `Z` or an offset such as `+00:00`: `timestampMs` reads anything else, an offset-less time or a lower-case `t` or `z` included, as no timestamp at all, rather than as whatever a JavaScript engine makes of it.

## Props

| Prop | Default | What it does |
| --- | --- | --- |
| `snapshot` | required | The progress snapshot to draw, or a newer one to consider. |
| `theme` | `"system"` | `dark`, `light`, or `system` to follow the environment, as `GraphViewer`'s theme mode. |
| `systemTheme` | — | The environment's theme when the host detects it itself, as on `GraphViewer`. |
| `paletteColors` | — | Sparse overrides of the palette's tokens, merged per key over the resolved theme's, as `GraphViewer`'s `config.paletteColors`. See "Styling". |
| `live` | `true` | While the run goes on, keep running bars growing between snapshots. |
| `now` | — | Pins the reading clock, as a timestamp or epoch milliseconds; the timeline then never ticks on its own. |
| `wideBatchThreshold` | `10` (`DEFAULT_WIDE_BATCH_THRESHOLD`) | A batch holding more items than this starts collapsed. |
| `timelineStyle` | `"detailed"` | The style the run is drawn in: `detailed`, described on this page, or `simple`, a checklist of the steps in the method's own words. Reactive, like `theme`. See [timeline-styles.md](timeline-styles.md). |
| `styleMenu` | — | Shows a style menu at the end of the header: `true` for every style, or a list of styles in the order offered. |
| `onTimelineStyleChange` | — | Called whenever the style changes, from the menu or the prop, never on mount. |
| `pipeRegistry` | — | The registry of the method's pipes, keyed by `pipe_ref`, as a `GraphSpec`'s `pipe_registry`, which the simple style titles its lines from. The detailed style does not read it. |
| `entryPipeRef` | — | The `pipe_ref` the run starts from, so the simple style lists the steps of a run that has not started yet. |
| `wideParallelThreshold` | `5` (`DEFAULT_WIDE_PARALLEL_THRESHOLD`) | In the simple style, a parallel with more branches than this folds its finished branches into one line. |
| `className` | — | Appended to the container's class list. |

**The reading clock.** A running invocation's bar grows to "now", and the timeline does not trust the page's clock to agree with the server's. It starts from the snapshot's `assembled_at`, the moment the snapshot was projected, and, while `live` is on, the run goes on and a drawn bar follows the clock (a running invocation's, or a canceled one's running to the end of the axis), advances it by the time the page has measured since, four times a second, the bars and the axis's ticks gliding together between repaints. With no bar following it, as while a run is pending, the clock does not tick and the timeline does not repaint. A newer snapshot moves the ticking clock to its own `assembled_at` when that is later than what the clock shows, and never back: a snapshot that took long to arrive can carry an `assembled_at` older than the moment the clock already shows, and the clock then carries on from what it showed, so no running bar and no axis shrinks and grows again. Only a clock that was itself ticking in the same stream holds it back this way: a clock that starts ticking, whether because a bar now follows it, because `live` came back on or because the host stopped pinning `now`, starts from its snapshot's `assembled_at`, never from a moment the host pinned. A snapshot of another stream starts the clock afresh. With `live={false}` each snapshot is drawn as of its `assembled_at`. A host that keeps a trusted clock of its own, or a replay, passes it as `now`.

While the clock ticks, only the axis and the rows whose bars follow it are drawn again: every timestamp is parsed once per snapshot (`snapshotTimes`), and a row whose bar the snapshot has settled, one that has ended or not started, keeps its props until the next snapshot. Its bar holds its place on the growing axis because a bar's position is an offset in milliseconds from the axis's start, which the stylesheet turns into a share of the track against the axis span the component sets on its body.

## What it draws

**The header** shows the run's status and the snapshot's `summary`, the one line the contract words for every reader, shown as it is and never parsed. When the run reads degraded, the run status's `degradation.message` shows beneath it, in its own words. A snapshot with no invocation draws no row: while the run is pending or running the timeline says nothing has started yet, and once it has ended, failed or canceled before anything started or read after its events expired, it says that no progress was recorded, which suggests no wait.

**One row per invocation**, labelled with its `pipe_code` and its place under its parent, worded as the summary words it: `step 2 of 4`, `branch 1 of 2`, `item 3 of 40`, each without its ` of …` when the parent carries no count. Rows nest by invocation path, children ordered by the number in their segment, and an invocation whose parent is missing from the snapshot nests under its nearest ancestor that is there, so a snapshot of part of a run, which starts at its `root_path`, draws the same way. A segment the grammar does not define is shown as written.

**The bar** runs from the start of the invocation's latest attempt to its end. Its colour gives the status: running, succeeded, failed, and the dimmed scheduled, skipped and canceled. A running bar is striped and grows to the reading clock; a skipped one is a dashed outline, since it ended with no output of its own; a canceled one recorded no end, so its dashed outline runs to the end of the axis. A scheduled item has no bar. The axis spans the earliest start to the reading clock while the run goes on, and to the latest time the snapshot recorded once it has ended, since an ended run's `assembled_at` is only when it was read; an end or a failure counts there even on an invocation whose start was not recorded. Its ticks fall at a round step that keeps them to the number its width has room for, in whole days past a day. The detail column on the right gives each row's duration, or its state when it has none.

**A batch is one collapsible row**, whatever its width. Its bar is a frame spanning the batch, with a thin strip of its items' states inside it, one cell per run of consecutive items sharing a state, and a failed item's cell never narrower than two pixels however many items share the bar. Its detail column reads the snapshot's counts, `12 of 40 done · 6 running · 1 failed`, the failed count shown when it is not zero. A batch holding more items than `wideBatchThreshold` starts collapsed and one that holds fewer starts expanded; the toggle beside its name switches it, and the timeline remembers the choice per batch for as long as it draws the same run. Collapsed, it still draws every item holding an invocation that failed or where the run is stuck (one carrying `degradation`), whether that is the item itself or anything beneath it, an item of a nested batch included, with everything under the item, so the trouble can always be pointed at along with the rows leading to it. The count of hidden items that a screen reader hears is worked out the same way. The counts are always the snapshot's own and never recounted from the rows: an item scheduled or canceled is counted in none of them. Bounding the rows of an expanded batch of several hundred items, by pages or by scrolling, is not done yet.

**A condition's branch carries the outcome it took.** Its row reads `outcome detailed`, or `default outcome`. When the condition has resolved, the name is its `selected_outcome`, the key it matched, which can differ from the key in the path: a path names an outcome group by the first key, in the order the outcome map declares them, that runs the group's pipe, so a condition that matched `medium` in a group whose first key is `low` has its branch at `outcome_low` while its row reads `outcome medium`, and a condition that took its default outcome reads `default outcome` even when its branch's path is a key's. A dry run's condition resolves nothing and runs every group, so each of its branches is named by its path. The row's tooltip says the condition took the outcome only when it resolved to it (`Took the outcome detailed`); a branch named by its path, as every branch of a dry run is, is only the branch for that outcome (`The branch for the outcome detailed`).

**Health annotations ride on their row**, the way a workflow engine's timeline marks a retried activity. An invocation whose work was tried more than once shows a `↻` badge: `attempt 2` in the warning colour while it is being tried again, its bar turned to the warning colour with it; `2 attempts` in a quiet tone once it has succeeded, the mark of a recovered invocation; and in the failure colour when it failed after them. Where its `last_failure` carries a time inside its bar, a tick marks that moment on the bar. The invocation where the run is stuck carries a `stuck` badge and a dashed outline around its bar. An annotation's text is in the row's tooltip with everything else the snapshot says of the invocation: the degradation's `message`, and the failure's problem by its `title` and its `detail`. `last_failure` is `{ problem, at }`, `problem` being the MTHDS problem document in the caller's view, typed as `Problem` from `mthds/errors` as a graph node's `error` is (see [run-problem.md](run-problem.md)): the problem that ended the invocation when it failed, and otherwise the latest failure of an attempt the engine is trying again, which the carrier serves as `runtime.unexpected` because the engine's own text is no problem document. An absent annotation means that nothing was observed, never that all is well.

## The pure surface

Everything the component decides is a pure function of the snapshot, exported from `./timeline` and unit-tested in the `__tests__/` directories beside it:

| Export | What it is |
| --- | --- |
| `ProgressSnapshot`, `ProgressInvocation`, `BatchProgress`, `ConditionProgress`, `InvocationFailure`, `ProgressDegradation`, `ExecutionAttempt` | The snapshot's types, named field for field after the contract. |
| `RUN_PROGRESS_STATUS`, `INVOCATION_STATUS`, `PROGRESS_MODE`, `DEGRADATION_REASON` | Its closed vocabularies as typed constants (the reasons are the ones emitted today, `reason` stays open). |
| `isRunEnded`, `timestampMs`, `compareTimestamps` | Whether a run has ended; a timestamp in epoch milliseconds, keeping digits past the millisecond as a fraction; and two timestamps ordered exactly, at every digit they carry. |
| `parsePathSegment`, `splitInvocationPath`, `parentInvocationPath`, `lastPathSegment`, `decodeOutcomeKey`, `invocationPathDepth` | The invocation path grammar. |
| `fresherSnapshot`, `isSameProgressStream`, `progressStreamKey` | The rule a reader keeps the fresher of two snapshots by, and the stream of progress a snapshot belongs to, as one string a reader can key its own state on. |
| `buildTimelineRows` | The rows a timeline draws, in drawing order, with their depth, place, outcome, batch strip and collapse state. |
| `timelineWindow`, `invocationBar`, `readingClockMs`, `timelineTicks`, `axisPercent`, `formatDuration`, `formatClockTime` | The shared axis, each bar on it, and the labels. |
| `snapshotTimes`, `invocationTimes`, `timelineWindowAt`, `barFollowsClock` | The same, with every timestamp parsed once per snapshot: the axis at any reading of the clock without parsing again, and which bars move while the clock ticks. |
| `buildInvocationTree`, `compareSiblings`, `isItemNode`, `isOutcomeNode`, `InvocationTreeNode` | The snapshot's invocations as the tree their paths make, each under its nearest ancestor the snapshot holds, siblings ordered by the number in their segment. |
| `TIMELINE_STYLES`, `TIMELINE_STYLE`, `TIMELINE_STYLE_IDS`, `DEFAULT_TIMELINE_STYLE`, `isTimelineStyleId`, `resolveTimelineStyle`, `resolveTimelineStyleMenu` | The registry of the timeline's styles: `detailed`, the default, and `simple`, each with its name and description. |
| `TimelinePipeRegistry`, `pipeOf`, `sequenceOf`, `stepAt`, `stepsAfter`, `stepNumberOf`, `sequenceMatches`, `joinedSequence`, `titleOf`, `joinBatch`, `qualifyPipeCode` | The join between a snapshot and the registry of the method's pipes, keyed by `pipe_ref`: a pipe's title, a sequence's steps by the number its invocation paths give them, and what a batch's one line is named after. |
| `buildSimpleProgress`, `SIMPLE_LINE_KIND`, `SIMPLE_LINE_STATE`, `SIMPLE_RUN_NOTE_REASON`, `SIMPLE_MAX_DEPTH`, `DEFAULT_WIDE_PARALLEL_THRESHOLD` | The simple style's projection: the run as lines of a checklist, each with its kind, state, title, counts and health, the run's own note, and where a failed run failed. |

`timelineWindow` and `timelineWindowAt` read a clock that is not a finite number as no clock at all, so the axis stretches to `assembled_at` instead and always has a finite end; `invocationBar` reads it the same way, so a running bar then ends at the end of the axis; and `timelineTicks` gives no tick for an axis whose span is not a finite positive number.

`buildTimelineRows` returns the same rows for the same snapshot and options, and keys nothing on time, which is what lets the component repaint on every snapshot while keeping each row it already drew in place: React keys each row by its path.

## Styling

The timeline uses the same semantic tokens as the graph viewer (`docs/theming.md`), applying the palette of its resolved theme inline on its own container, so it themes correctly with no viewer in the tree. A host changes its colours with `paletteColors`, as it does `GraphViewer`'s with `config.paletteColors`: a sparse map of tokens, such as `{ "--color-success": "#16a34a" }`, merged per key over the theme's palette, so every token it does not name keeps following the theme. A `--color-*` or `--surface-*` declared on the container's class in a stylesheet does not change it, because the palette's inline declarations win over a stylesheet's ordinary ones. Variables on `.mthds-run-timeline` set its layout: `--mthds-run-timeline-name-width` (the name column), `--mthds-run-timeline-meta-width` (the detail column) and `--mthds-run-timeline-indent` (each nesting level's indent). `--mthds-run-timeline-axis-span`, which the component sets on its body as the axis grows, is not one of them. Below 560 pixels of width each row moves to two lines, its name and detail above and its bar across the whole width below. Rows fade in as they appear and running bars' stripes move, both stilled under `prefers-reduced-motion`.

**How a host sizes it.** The timeline takes the full width of its container and the height its rows need. Its width never comes from what it holds: it is an inline-size container, which is what lets its rows move to two lines when it is narrow, and the content of such a container does not size it. In a block container it fills the width, and as a flex item in a row it takes the whole row, sharing it with its siblings as flex items do, so give a sidebar beside it a fixed basis. A container that sizes itself to its content, such as an `auto` grid track, an inline block or a float, has no content width to give it, so the host gives that container a width of its own (a `1fr` or fixed track, an explicit width) rather than leaving it to its content.

## The stories

`make storybook` and open **Timeline / RunTimeline**; the simple style's stories and the style menu's are described in [timeline-styles.md](timeline-styles.md#the-stories). `RecordedRun` replays the contract's worked example from its first event to its end, one snapshot per change, with play, step and speed controls: rows appear as invocations start, bars grow and settle, the condition's chosen branch and the parallel's branches appear under it, the batch's items appear with their steps, item 2's second step is tried again and keeps its attempts once it recovers, and item 3 shows where the run is stuck until it advances. `WideBatch` replays a batch over twenty-four filings, collapsed into one row whose failed item stays in view. `WorkedExample` draws the contract's mid-run snapshot exactly as the contract prints it, and the other stories cover the light theme, a canceled run, a run not yet started, a run that failed before it started, a dry run's condition, a host's palette override, reads answering out of order, a slow read the self-ticking clock must not jump back for, a clock a host pins and then releases, and the timeline as a flex item beside a sidebar. Their play functions are the component's browser tests.

The recorded runs are written by hand in `src/timeline/react/__stories__/recordedRuns.ts`: each invocation with its start and end, each fan-out and resolution, and what the engine reported of the run's health over time. `runRecorder.ts` stands in for a carrier, projecting a recording at any moment into a contract-shaped snapshot, its `summary` worded by the contract's rule, and `src/timeline/__tests__/recordedRuns.test.ts` holds it to the contract: the recording of the worked example's run, taken at the example's moment, equals the snapshot the contract prints, version and summary included.
