# Standalone static graph — deferred follow-ups

Findings from the review of `feature/Standalone-static-graph` (item L-260925-940363) that were confirmed and deliberately not fixed on that branch.

## From the round 1 `/rev` pass (profile 3, bar `open`, reviewed at `c84eded`)

- **`hasTopLevelMainPipe` reads inside multiline strings** (Codex, `src/static-graph/sourceOrder.ts:36-42`). The scan is line by line and has no notion of a TOML multiline string, so text inside a top-level `description = """…"""` or `system_prompt = '''…'''` is read as TOML. A line such as `[example]` inside the string ends the scan early and returns `false` although a real `main_pipe` follows, and a line such as `main_pipe = "fake"` returns `true` for a file that declares none. Confirmed by the verifier end to end: with `alt.mthds` (declaring `main_pipe = "alt_run"`) and `bundle.mthds` (a multiline `description` containing `[example]`, then `main_pipe = "bundle_run"`), the graph is drawn from `alt_run`; without the multiline string, `bundle.mthds` leads and the graph is drawn from `bundle_run`.
  - **Why deferred:** it only changes the result when two or more files declare `main_pipe` and one of them carries such a line inside a top-level multiline string placed before its `main_pipe` or its first table. A method where a single file declares `main_pipe` is unaffected, because the merge finds the real `main_pipe` whatever the order. None of the `.mthds` files under `data/` has a top-level multiline string in that position. The VS Code extension's private copy of the scanner has the same limitation.
  - **Fix shape:** track whether the scan is inside a `"""` or `'''` string (an opening delimiter on a `key = ` line without its closing one on the same line) and skip lines until the closing delimiter. Keep it a lenient scan rather than a TOML parse: the scan exists because an editor asks about half-written files.
  - **Verify with:** a `hasTopLevelMainPipe` test for each direction (`[example]` and `main_pipe = "fake"` inside a multiline string), and an `orderMthdsSources` test with the two-file case above.

## From the round 1 `/rev` pass after the reset (profile 3, bar `open`, reviewed at `9dae971`)

- **`loadFromSources` repeats the steps of `buildStaticGraphSpecFromToml`** (cubic, verified; `src/standalone/loadEmbeds.ts:53-69` against `src/static-graph/buildStaticGraphSpec.ts:111-127`). The standalone loader parses each file, merges and walks, in the builder's own order, so that each parse note can carry its file's name. It is faithful today: the loader passes no options and the builder defaults to none, and the diagnostics come out in the same order. The risk is future drift, since a new option, stage or diagnostics order added to the builder would reach every host except the standalone page.
  - **Why deferred:** there is no failing input, and removing the duplication needs new public API, because the builder takes `string | string[]` and `Diagnostic` (`src/static-graph/types.ts`) has no `file` field. That is more surface than the few lines it would remove.
  - **Fix shape:** give `Diagnostic` an optional `file`, let `buildStaticGraphSpecFromToml` accept `MthdsSource[]` and stamp each parse note with its source's name, have `staticDiagnosticsToValidationIssues` carry `file` through, and reduce `loadFromSources` to one call plus `validateGraphSpec`.
  - **Verify with:** the existing `src/standalone/__tests__/mthdsSourcesEmbed.test.ts`, which asserts the file name on a parse note, passing unchanged after `loadFromSources` stops calling `parseMthdsBundle` itself.

## From the round 3 `/rev` pass (profile 3, bar `necessity`, reviewed at `e7a47c8`)

These three findings are **unverified**: they sorted below the `necessity` bar, so no verifier read them, and each rests on its reviewer's word alone. Confirm one before fixing it.

- **The `</style` check in `inlineHazards` matches a bare prefix** (Codex, unverified; `scripts/inlineHazards.mjs:70-73`). Per the HTML spec, a raw-text end tag closes `<style>` only when `style` is followed by a tab, newline, form feed, space, `/` or `>`. The check fires on the prefix alone, so harmless CSS such as `/* </stylesheet> */` would fail the standalone build.
  - **Seen while verifying a neighbouring finding** (checked with parse5 8.0.1 and jsdom 30.0.1): the `<script` check in an unclosed `<!--` section has the same over-breadth, because the regex's `\s` is wider than HTML's whitespace. `<script` followed by `\v`, U+00A0 or U+2028 is flagged, and so is `</scripts>`, although neither affects the page. It also has one gap: JS that _ends_ in `<script` after an unclosed `<!--` is approved, and the template's following newline then completes the double-escape start and swallows the page. esbuild ends every bundle with a licence comment (`*/\n`), so the current build cannot produce that input.
  - **Why deferred:** every over-rejection fails the build loudly rather than shipping a broken page, and the one gap is unreachable with the current bundler output.
  - **Fix shape:** require the end-tag delimiter `[\t\n\f />]` after `style` and `script`, use that same class in place of `\s` for the double-escape start, and treat a `<script` at the very end of the checked text as a hazard when it sits in an unclosed section.
  - **Verify with:** `inlineHazards.test.ts` cases for `</stylesheet>`, `</scripts>`, `<script\v`, and `a="<!--";b=1;x<script` at the end of input.
- **A `null` `pipelex-graphspec` beside `mthds-sources` is not treated as "embeds both"** (cubic, unverified; `src/standalone/loadEmbeds.ts:88`). The loader decides whether the sources embed is present from its text, but decides whether the graphspec is present from its parsed value. So a page whose `pipelex-graphspec` holds JSON `null` and that also carries `mthds-sources` draws the sources silently, where `docs/static-graph.md` and the changelog say it should show the error screen.
  - **Why deferred:** only a page written by hand with a literal `null` graphspec reaches it, and the result is a drawn method rather than lost data.
  - **Fix shape:** decide both presences the same way, from `isBlankScriptText(texts.graphspec)` as well as `isBlankScriptText(texts.sources)`.
  - **Verify with:** a `standaloneLoad.test.ts` case with `pipelex-graphspec` holding `null` beside a valid `mthds-sources`, expecting the error screen.
- **The `unvalidated` changelog entry lacks the `(Breaking)` marker** (cubic, unverified; `CHANGELOG.md:13`). The entry says a TypeScript host with an exhaustive `switch` or `Record` over `ValidationState` must add the new member, which is a breaking change under the workspace changelog rule.
  - **Why deferred:** it is below the round's bar, and the entry is still under `[Unreleased]`, so it can be corrected before any version ships it.
  - **Fix shape:** append `(Breaking)` to the entry's bold title, at the latest when `/release` cuts the version.
