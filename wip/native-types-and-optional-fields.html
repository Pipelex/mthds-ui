mthds-ui · engineering note

Native types & optional fields

Two independent rendering bugs, both discovered while giving the temporal native concepts real coverage, both of which made a concept panel quietly describe the wrong thing. Plus the sweep onto pipelex 0.41.0 that surfaced them.

release v0.16.0 2026-08-11 #64 catalog #69 optional fields pipelex#1089

TL;DR

  1. The static graph did not know YesNo, Date and Time exist. Our hand-kept native catalog was missing three codes, so a .mthds typing an output as Date got it resolved as an ordinary concept of the authoring domain — blank description, wrong domain, synthetic structure class, and a refines chain pointing at nothing. Nothing threw. Static mode only. Fixed by adding the three codes and copying the standard's wording verbatim.
  2. The dry-run concept panel hid every optional field. SchemaTable filtered the structure table down to required fields whenever isDryRun was set. In dry mode that table is the only view, so the filter landed on a concept description and made it lie: native.Date is date + optional time, and the panel asserted date-only. It also made the req badge column vacuous. Deleted.
  3. The blast radius of #2 was much bigger than first thought. It was noticed on the natives, but it applied to most of the dry corpus — any concept with an optional property. Roughly a dozen authored concepts across the fixtures rendered incorrectly.
  4. Both are now guarded by tests that point in opposite directions: a pinned code list (catches our edits) and a corpus oracle that checks our catalog against pipelex's own output (catches upstream drift, for any native a fixture actually references).
  5. Supporting work: swept onto pipelex 0.41.0 (two breaking blueprint-type changes), fixed the date/datetime/time JSON-schema mapping, taught the parser the type-less PipeSignature, and added three fixture pipelines so all of this is exercised by the sweeps that auto-discover data/pipelines/pipeline_*.

Where each bug lives

The two bugs sit on different rendering paths, which is why they went unseen independently and why fixing one did not reveal the other. Worth holding in your head before the details:

Path Where the concept metadata comes from Which bug applied
static Our own parser — src/static-graph/ reads the .mthds TOML. No Python, no run. Bug A — our catalog was the only authority, and it was wrong.
dry pipelex's own concept_registry, emitted by a dry run. Always correct. Bug B — the data was right; the panel filtered it before rendering.
live Same as dry, plus real payloads. Neither. Non-dry rendering never filtered.

Bug A — three natives missing from the catalog

PR #64 · src/static-graph/conceptRefs.ts

conceptRefs.ts carries a hand-kept mirror of the MTHDS native concept set. That table is what decides whether a bare Date resolves into the native domain or falls through to the domain being authored. YesNo, Date and Time were never added to it — so every one of those refs silently degraded into a stub.

The satisfies + keyof pair is the load-bearing part beyond the three new rows. The old signature took a bare string with a ?? code fallback, so any string could be passed in and would produce a plausible-looking native with its code as the description. Now a caller cannot mint a native the catalog lacks — the compiler stops it.

Also fixed here: six descriptions had drifted into paraphrases

The catalog's wording is display-only, but it is copied from the standard's pinned set, and the copies had rotted. These are now verbatim:

Code Was (paraphrase) Now (verbatim)
Dynamic Dynamically typed content A dynamic concept
TextAndImages A text with images A text and an image
Page The content of a page of a document The content of a page of a document, comprising text and linked images and an optional page view image
JSON JSON content A JSON object
SearchResult A search result A search result with answer and sources
Composite A named composition of multiple contents A named composition of contents

The authority chain is now written down in the file header: the standard's docs/spec/native-concepts.md wins, pipelex mirrors it, we copy pipelex. If the mirror and the spec page disagree, the spec page wins.

Known gap, deliberately left open

The catalog still does not carry the natives' pinned structures. nativeConceptInfo has never populated json_schema, so in static mode a native's concept panel reads "Schema not available" where a dry or live spec shows a field table. That is why Bug B below is a dry-mode story, not a static one.

Bug B — the dry-run panel hid every optional field

PR #69 · src/graph/react/detail/ConceptDetailPanel.tsx

SchemaTable filtered its rows down to required fields whenever isDryRun was set. The filter has been there since the original "pipe cards" commit (943dbfe) and was never touched.

The rationale a required-only filter would need is "an absent optional value has nothing to show" — which is an argument about a data view. In dry mode there is no data view: ConceptBody computes hasData = Boolean(ioData) && !isDryRun, so the panel deliberately suppresses pipelex's fabricated dry payloads and returns the structure view directly. The filter therefore landed on a concept description, where an optional field is not missing data — it is the single most important thing the concept has to say.

The change

Almost entirely a deletion. Note what is not touched: isDryRun keeps its other job on ConceptDetailPanel — suppressing fabricated dry payloads — and the GraphViewer plumbing that passes it in is unchanged. Only the SchemaTable prop goes away.

The scope was bigger than the first analysis claimed

The original write-up asserted this was "only invisible for authored concepts, because pipelex marks authored structure fields required". That is wrong. Sweeping the committed dry corpus turned up optional properties on recruitment.CandidateProfile, recruitment.MatchScore, content_moderation.SafetyScore, cv_matching.CvEvaluation, cv_batch_screening.JobRequirements and CandidateProfile, and rfp_qualification.CapabilityMatch. The natives are where it was noticed, not where it applied — this fix changes rendering across most of the dry corpus.

War story: the test that passed for the wrong reason

ConceptDetailPanel.test.ts looked like it protected dry-run data suppression. It did not. The fixture's schema declared an optional field named generated_summary, and the fixture's data payload had a key spelled the same way. The assertion was: 

expect(html).not.toContain("generated_summary");

…which was satisfied by the schema-field filter, not by the data suppression it claimed to test. Deleting the filter made the optional schema field correctly render — and the test failed. That failure was the fix working.

The fixture was restructured so schema field names and payload strings are disjoint, and the dry-mode test now asserts all three things it should: structure renders, the optional field is visible, and fabricated payload values are not.

A second pass caught the same trap one field over: the payload's key was summary, spelled exactly like the optional schema field the new regression case asserts on — and StuffViewer renders payloads via JSON.stringify, so keys reach the same HTML the schema assertions read. Payload keys are disjoint now too.

Lesson worth keeping: when an assertion is not.toContain, make sure exactly one mechanism can satisfy it.

What else moved

The 0.41.0 sweep — two breaking blueprint-type changes

PR #63

The bundled MTHDS JSON Schema is generated from pipelex's blueprint models and gitignored there, so drift never shows up in a PR — our copy had fallen behind. Refreshed to 0.41.0, which added datetime and time to concept structure field types: a .mthds declaring either was valid at runtime but rejected by our copy.

Two type declarations were wrong in the same way — both declared required:

  • PipeLLMBlueprint.llm_prompt_spec.templating_style — removed. It cached a derived value; the style now travels as a make_llm_prompt parameter, so the key is absent from every dump. No component ever read it. Careful: TemplateBlueprint.templating_style is a different field, still live, easy to confuse when grepping.
  • PipeParallelBlueprint.combined_output — made optional, not removed. A parallel always combines now, so 0.41 omits the key — but the static builder still reads it as a legacy authoring key when naming the combined stuff.
Temporal field types were mapped to the wrong JSON schema

Squarely the natives' business: native.Date's pinned structure is date + time, and native.Time's is time. Our TOML→JSON-schema derivation had no entry for either, so both fell through to an untyped string — and date still carried date-time from before datetime existed as its own type.

src/static-graph/parseMthdsBundle.ts
 const FIELD_TYPE_TO_JSON: Record<string, Record<string, unknown>> = {
   …
-  date: { type: "string", format: "date-time" },
+  date: { type: "string", format: "date" },
+  datetime: { type: "string", format: "date-time" },
+  time: { type: "string", format: "time" },
   …
 };

This corrects the json_schema a static GraphSpec hands to hosts. It changes nothing on screen in this repo — our type column reads type and ignores format (along with enum, items and default). That reader gap is still open.

The type-less PipeSignature, and the hole it was leaving in the graph

A signature has no type in .mthds — omitting the type is the signature. But normalizePipe still demanded a type from the known-classes set, so it reported unknown-pipe-type and dropped the pipe. The step that called it then failed to resolve and vanished from the graph entirely, edges included — a hole plus two panel errors, on exactly the half-written methods the static graph exists to render. 

+  if (typeValue === undefined) {
+    // A typeless section is a signature — but only if it declares nothing
+    // beyond the contract, and `output` is present (the schema requires it).
+    const isSignature =
+      raw.output !== undefined &&
+      Object.keys(raw).every((key) => SIGNATURE_ONLY_KEYS.has(key));
+    if (isSignature) return "PipeSignature";
+  } else if (typeValue === "PipeSignature") {
+    // Retired in 0.41. Tolerated with a warning rather than dropped: erroring
+    // would delete the pipe — and with it the whole calling step.
+    ctx.diagnostics.push({ severity: "warning", code: "retired-signature-tag", … });
+    return "PipeSignature";
+  }
The subtlety worth internalizing

KNOWN_PIPE_TYPES now serves two surfaces that disagree: the GraphSpec pipe_type / registry dump does carry PipeSignature (the runtime class serializes its tag normally), while the authored .mthds surface does not (the blueprint excludes the tag). Only normalizePipe reads the authored surface, so the split lives there — validateGraphSpec must keep accepting the type.

The retired type = "PipeSignature" spelling still renders, now with a retired-signature-tag warning carrying pipelex's own migration wording. Tolerated, not supported — rejecting it would re-open the exact hole above for anyone mid-migration.

Making it hard to break again

Three fixture pipelines, so the sweeps actually see the natives

Before this, the only bundle exercising these natives was an inline Storybook string — invisible to every fixture-driven sweep in the repo, and not even runnable by pipelex. Three real bundles in data/pipelines/ replace it, which means they are picked up with no wiring by the sweeps that auto-discover pipeline_*: parse, static build, static↔dry parity, and the new corpus oracle.

Meeting Triage — the four resolution paths in one graph

Date[], Time and a bare YesNo as stuff nodes, plus a local concept refining a native. Exactly the paths Bug A touched. 

domain      = "scheduling"
main_pipe   = "triage_request"

[concept.Verdict]
description = "Whether the meeting request is accepted"
refines     = "YesNo"          # ← the refinement chain that pointed at nothing

[pipe.read_dates]
type   = "PipeLLM"
output = "Date[]"              # ← resolved as scheduling.Date before #64

Also the standing end-to-end check for the temporal natives: make fixtures-live ONLY=pipeline_32.

Availability Routing — the natives through the controllers

Where the graph machinery has to actually operate on a native: batch_over a native Date[] driving a PipeBatch fan-out with per-item stuff, and a PipeCondition branching on a native's structure field (urgent.yes_no).

Static↔dry parity holds for both, with no accepted divergences.

All Native Concepts — breadth for the oracle

One PipeLLM per remaining native output — Number, Html, TextAndImages, JSON — purely to lift the corpus oracle's coverage to every catalog code except Dynamic, which has no authorable output position.

Both bundles now run live, thanks to an upstream fix

pipeline_32 and pipeline_33 shipped with placeholder LIVE specs (the DRY spec re-tagged — the only two in the repo) because a PipeLLM outputting Date, Date[] or Time failed pydantic validation on every real model response. A mode="before" field validator forfeited pydantic's strict-JSON acceptance of ISO strings, and instructor validates structured output in strict mode. Fixed in pipelex#1089; both were regenerated against real inference in PR #68.

Two tests, pointing in opposite directions

The corpus oracle sweeps every data/pipelines/*/dry_run_graph_spec.json and, for each concept_registry entry with domain_code === "native", asserts the code is one we know and that its description and structure class name match exactly. Adding a bundle that uses a native is what brings that native into scope — which is what the three new pipelines do.

It fails in a confusing place — this is expected

Regenerating pipeline fixtures can break a native-concepts unit test. That is the oracle doing its job: pipelex reworded a description or renamed a structure class. Fix conceptRefs.ts, not the test. The file carries a failure guide at the top saying so.

Smoke-story drift, caught in passing

PipelineSmoke.stories.tsx renders each fixture through GraphViewer in a real browser and asserts nodes appear — but it is hand-written (Storybook indexes static exports, so the stories cannot be generated in a loop), and it had drifted. Pipelines 26, 28, 30 and 31 were each added to the catalog without a smoke story, across four separate changes, with nothing to notice.

All four are added, and fixturesConsistency.test.ts now fails — naming the missing key — when a catalog entry has no smoke story. PR #66

What to carry forward

  1. A hand-kept mirror needs an oracle, not just a pinned test. Pinning our own list against our own list catches typos, never drift. The corpus oracle works because the specs are pipelex's output — something we did not author.
  2. "Dry mode" is not "a run with no data" — it is a different view entirely. Any rendering branch keyed on isDryRun deserves the question: is this about the data, or the description? A filter that makes sense for one is a lie in the other.
  3. If a UI column exists to convey a distinction, never filter on that distinction. The req badge and the required-only filter cannot both be right.
  4. Inline test bundles don't get swept. If a feature is only exercised by a string inside a story, none of the repo's fixture-driven checks can see it. Put it in data/pipelines/.
  5. Two surfaces can share a name and disagree. PipeSignature is a member of the registry pipe_type set and not of the authored .mthds set. Check which surface you are validating.
