# The form kernel's stylesheet in a host that has Tailwind 4

Since v0.21.0 both React entries import `src/styles/form-kernel.css`, which is one line: `@import "@pipelex/mthds-form/styles.css" layer(mthds-form);`. The kernel's `styles.css` is a complete Tailwind build, with preflight plus every utility the controls use, unprefixed and unscoped. The layer was meant to make that sheet safe in any host, and the stylesheet's comment, `docs/run-form-panel.md`, the README and the regression test all say so in the same words: layered rules lose to unlayered rules regardless of source order, so the host keeps everything it declares, and nothing changes for a host with no Tailwind.

The item reports that this holds only for a Tailwind 3 host. This document records the verification, which confirms the item and finds two more false claims in the same paragraph, and then proposes a fix that removes the requirement rather than only documenting it.

**Ratified 2026-09-25** by the owner, as recommended: Decision 1 is B with C, Decision 2 names the two host stylesheets as below, and Decision 3 documents Tailwind 3 and prefixed Tailwind 4 hosts as unsupported. Before ratification the draft was put to an adversarial review by Codex, whose accepted objections are folded in below and listed under "Review" at the end.

## What was verified, and how

The reproduction compiles a small host stylesheet with Tailwind `4.3.3` through `@tailwindcss/postcss`, the same plugin a Next.js host runs, scanning a page that carries `w-full md:w-[180px]` on a sidebar, `flex flex-col md:flex-row` on its container and `hidden sm:inline` on a label. It then loads that host sheet in headless Chromium at 1280px, followed by a second stylesheet containing exactly what `form-kernel.css` contains, pointing at the real kernel `0.8.0` `styles.css`. The second sheet arrives after the host's, as the graph chunk's does. A button carrying `px-3 border rounded-md h-9`, which the host's own build did not generate, stands in for a kernel control that a host did not compile itself. A page with no Tailwind at all and a `<h1>`, a `<ul>` and a `<p>` left to the browser's defaults stands in for a host without Tailwind.

| Host                                         | Sidebar | Main   | `hidden sm:inline` | Kernel-only button padding / border | `h1` size, `ul` marker, `body` margin |
| -------------------------------------------- | ------- | ------ | ------------------ | ----------------------------------- | ------------------------------------- |
| Tailwind 4, kernel sheet appended (today)    | 1280px  | 1280px | `none`             | 12px / 1px                          | —                                     |
| Tailwind 4, `@layer mthds-form;` named first | 180px   | 1100px | `inline`           | **0px / 0px**                       | —                                     |
| No Tailwind, alone                           | —       | —      | —                  | —                                   | 32px, `disc`, 8px                     |
| No Tailwind, kernel sheet appended           | —       | —      | —                  | —                                   | **16px, `none`, 0px**                 |

### The reported defect is confirmed

A Tailwind 4 host keeps its theme, base and utilities in real cascade layers. A layer ranks by where the document first names it, and the host's compiled sheet names `theme, base, components, utilities` before the kernel sheet arrives, so `mthds-form` is named last and ranks above the host's `utilities`. From that point the kernel's bare `.w-full`, `.flex-col` and `.hidden` beat every responsive variant the host writes: in the reproduction the sidebar took the whole row, the container fell back to a column, and the label disappeared. The two Tailwind 4 host applications that consume this package each found this in their own layout and each fixed it in their own stylesheet by naming the layer first. Their fixes are the evidence cited on the item.

### Naming the layer first is necessary, and it is not sufficient

The item's proposed documentation is "a host with Tailwind 4 names `@layer mthds-form;` as its first statement". The second row shows what that does to a kernel class the host did not compile itself: the button loses its padding and its border. Named first, `mthds-form` ranks below every host layer, including the host's `base`, and Tailwind 4's preflight there sets `margin: 0; padding: 0; border: 0 solid` on every element. A utility that loses a layer contest loses it whatever its specificity, so every kernel utility that touches a property preflight also sets is overridden.

The two hosts are unaffected only because both also scan the kernel's shipped JavaScript with `@source`, so every class a control uses is compiled into the host's own `utilities` layer and the kernel's copy is never needed. That is the opposite of what this package documents today: `docs/run-form-panel.md` and the README tell a host not to add the kernel to its content globs. For a Tailwind 4 host, the only arrangement that works is to compile the kernel's classes itself and rank the kernel sheet lowest, at which point the sheet does nothing at all.

There is a second cost to that arrangement. Under pnpm, a transitive dependency is not linked into the host's root `node_modules`, so an `@source` path into `node_modules/@pipelex/mthds-form` resolves only when the host declares the kernel as a direct dependency of its own. One of the two hosts does exactly that, at the range this package resolves, with a test to keep the two ranges equal. That is the declaration this package's own documentation forbids, because a mismatched range gives the tree a second copy of the kernel and a second React context identity.

### The claim about a host with no Tailwind is false

"Nothing changes for a host with no Tailwind: a layer only decides conflicts, and there are none to decide." The last row contradicts it. Author styles outrank the browser's default styles whatever layer they sit in, so the kernel's preflight overrides every browser default the host did not restate: headings drop to body size, lists lose their markers, and paragraphs and the body lose their margins, across the whole page, the moment a graph mounts. This is the same class of failure the layer was introduced to stop, in the host kind the documentation says is safe. The VS Code extension's webview is such a host; it is a dedicated panel whose shell expects the kernel's preflight, so it is not harmed, but a host that embeds a graph in a page of ordinary content would be.

### One reason given for naming only the layer does not reproduce

The item and both hosts' stylesheet comments advise naming only `mthds-form` rather than Tailwind's whole order, because an unnamed `properties` layer would then sort after `utilities`. At Tailwind `4.3.3` the compiler emits `@layer properties;` above everything the host writes, including a host's own leading `@layer` statement, so spelling the whole order out ranks `properties` correctly. A probe rule placed in both layers confirmed it. The advice to name only `mthds-form` is still right, for a simpler reason: it does not depend on the list of layers a given Tailwind version defines.

### Tailwind 3 hosts were already outside what the layer can serve

Kernel `0.8.0` ships Tailwind 4 class names, which a Tailwind 3 build cannot compile, so a Tailwind 3 host depends entirely on the kernel sheet. Its preflight and its utilities are both unlayered, and a layered kernel utility loses to both, so the controls lose their padding and borders. Without the layer the kernel's `.hidden` beats the host's variants again. No position serves such a host. No current consumer is one: the one Tailwind 3 site in the workspace imports only `./shiki`.

## Why no position in the cascade can fix it

A complete Tailwind build is two things with different needs. Its preflight must rank below the host's own base styles, or it resets the host's base, as the kernel's `border: 0 solid` once did to every host border colour. Its utilities must rank above the host's base, or preflight strips them, and below the host's utilities, or they beat the host's variants. An `@import … layer()` gives the whole sheet one position. It cannot interleave the halves of one sheet with the layers of another. So the layer settles the question for exactly one kind of host, a host with no Tailwind of its own, and even there it cannot stop the preflight from reaching the host's page.

This means the decision to make is not where the layer goes. It is who loads the kernel's sheet. A host that has Tailwind 4 should compile the kernel's classes itself and never load the sheet. A host without Tailwind needs the sheet, preflight included, and should load it knowing what the preflight does to its page.

## Options

**A. Keep injecting the sheet and document the requirement.** This is the minimal fix the item asks for. A Tailwind 4 host names `@layer mthds-form;` first, adds `@source` for the kernel, and under pnpm declares the kernel directly so that the path resolves. The layer name becomes a public contract. Nothing breaks for any consumer. The cost is three coordinated requirements in every Tailwind 4 host, a complete Tailwind build that is downloaded and parsed there and never applies, a preflight that still reaches the page of every host without Tailwind, and a documented instruction to make the direct kernel declaration the rest of the documentation forbids. A Tailwind 4 host that misses one of the three gets either its own layout broken, only after a graph has loaded and only until a reload, which both hosts had to debug to attribute, or controls with no padding or borders.

**B. Stop injecting the sheet, and let each kind of host load what it needs.** The React entries import no kernel stylesheet. A host with Tailwind 4 compiles the kernel's classes, following the kernel's own documented Tailwind 4 setup. A host without Tailwind imports the layered sheet explicitly. There is no cross-package cascade-order contract left, no inert stylesheet in a Tailwind host, and no preflight in a page that did not ask for it. This is a breaking change for a host without Tailwind, which renders unstyled controls until it adds its import. The failure is visible on the first render and the documentation names the fix. A host with Tailwind 4 that forgets its line gets the failure that predates v0.20.0: controls that are mostly styled, because the classes they share with the host's own markup survive, while the ones only the kernel uses are missing.

**C. Ship the Tailwind 4 host's line from this package.** The package ships `tailwind.css`, a stylesheet holding only the `@source` directives that find the kernel's shipped JavaScript relative to this package's own location, so that a host writes `@import "@pipelex/mthds-ui/tailwind.css";` and never names a path into `node_modules`. A spike settled the question this depends on. Tailwind `4.3.3` resolves an imported package stylesheet to its real path and resolves that file's `@source` directives relative to it, and an explicit `@source` is scanned even inside `node_modules`. From `dist/styles/` inside the package, `../../../mthds-form/dist` finds the kernel in a pnpm virtual store, where it is a sibling of this package, and in a hoisted npm tree. `../../node_modules/@pipelex/mthds-form/dist` finds it when npm nests it under this package. A path that does not exist is skipped without an error, so the file lists both. The spike built a stand-in pair of packages, laid out as pnpm, hoisting npm and nesting npm each lay them out, and compiled a class used only in the stand-in kernel's JavaScript under all three, and under a pnpm layout where the host also declared the kernel directly. It did not run against the published packages or a real host's build; the plan's smoke test and host check do. The host no longer needs a direct declaration of the kernel, and the file scans exactly the copy of the kernel this package imports. C combines with either A or B.

C replaces one line of the kernel's Tailwind 4 host setup, not the setup. Scanning finds class names; the host's theme is what compiles them. The kernel's `docs/theming.md`, "A host that runs Tailwind", is the contract: the host imports `tw-animate-css`, whose utilities the select popover's and the tooltip's transitions use, and maps the shadcn tokens under `@theme inline` so that `--color-background`, `--color-foreground`, `--color-border`, `--color-input`, `--color-ring`, the `primary`, `secondary`, `destructive`, `muted`, `accent`, `popover` and `card` pairs and `--radius-lg`, `-md` and `-sm` resolve. Without that mapping, `bg-background` compiles to nothing, whatever the scan found. A shadcn/ui Tailwind 4 codebase already has both. What C removes is the kernel's `@source` line, which names a path into `node_modules` and, under pnpm, needs the direct declaration. The package does not ship the token mapping itself: the mapping is the host's design system, and an `@theme` block arriving from a package is exactly the kind of cross-package override this design exists to remove.

**Rejected.** Prefixing or scoping the kernel's utilities under a container class would put the fix in the kernel's build, and would still fail for Radix popovers, which portal their content outside any container this package owns. Injecting a `<style>@layer mthds-form;</style>` at the top of `<head>` from JavaScript would rank the sheet lowest with no host involvement, but it acts on the host's document from a library, it is absent from server-rendered HTML, and a Content Security Policy can forbid it. It would also still leave every kernel utility losing to the host's preflight. Deriving a preflight-free copy of the kernel's sheet at this package's build time would put a copy of the kernel's CSS in this package's `dist`, frozen at the kernel version this package was built against rather than the one the host resolves.

## Decisions

### Decision 1: stop injecting the kernel's sheet (B with C)

Recommended: **B with C**. The comparison that decides it is what a host that misses its requirement sees:

| Host        | Misses its requirement under A with C                                                                                                 | Misses its requirement under B with C              |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| Tailwind 4  | Its own layout breaks after a graph loads, or the controls lose padding and borders if it named the layer without scanning the kernel | The controls miss the classes only the kernel uses |
| No Tailwind | Nothing to miss, but its page loses the browser's default styles when a graph mounts                                                  | Unstyled controls on first render                  |

Under A the worst failures land in the host's own interface, appear only after a graph has loaded, and have now been debugged twice by people who could not see where they came from. Under B every failure lands in the controls this package renders. That is not the same as being easy to see: for a Tailwind 4 host, partial styling is the silent failure this repository's own history records, which read like a broken design system rather than a missing line. B's advantage there is narrower than visibility. The failure stays inside this package's components instead of spreading to the host's, the setup is the kernel's own documented one rather than a second contract, and the package side of it is held by a smoke check that compiles a minimal host against the published tarball. B also brings this package in line with the kernel's own documented model, in which a host with Tailwind scans the kernel and a host without it imports the prebuilt sheet, and it removes the one reason any host has for declaring the kernel directly.

The reason v0.20.0 made the import this package's job was that hosts forgot the Tailwind 3 content glob, which had to reach into `node_modules` and silently matched nothing. Under B with C the Tailwind 4 host imports a stylesheet by package name, which is the gesture it already makes for `tailwindcss` and `tw-animate-css`, and no host ever writes a path into `node_modules`. That removes the part of the old lane that failed. It does not remove the need to remember a line: no arrangement can do that for a host with Tailwind, because under A that host must remember three.

A with C was the fallback, not taken. It would have shipped `tailwind.css` with a leading `@layer mthds-form;` so that one import, placed before `@import "tailwindcss"`, both names the layer and scans the kernel. That import would have been order-sensitive, the layer name would have become a contract, and the preflight would still have reached the pages of hosts without Tailwind.

### Decision 2: the two host stylesheets and their names

- `@pipelex/mthds-ui/tailwind.css` is shipped from `src/styles/tailwind.css` to `dist/styles/tailwind.css`. It holds the two `@source` candidates and a comment saying what they are for. No JavaScript imports it. A Tailwind 4 host adds it to the run of `@import`s in its entry stylesheet, in any position within that run, since `@source` does not depend on order, in place of the `@source` line of the kernel's documented setup. The rest of that setup, `tw-animate-css` and the token mapping, stays the host's.
- `@pipelex/mthds-ui/form-kernel.css` is the existing `src/styles/form-kernel.css`, now exported for a host without Tailwind to import once. It keeps its `layer(mthds-form)`, because in such a host the layer is what lets the host's own rules win ties against the kernel's utilities. The layer name stops being anything a host has to spell, and the two Tailwind 4 hosts' leading `@layer mthds-form;` becomes a harmless statement they can delete.
- Neither file is ever imported from JavaScript. The "CSS Packaging" rule in `CLAUDE.md` describes stylesheets that are imported from JavaScript and must survive the bundler, so it gains a short paragraph for stylesheets a host imports itself: they need the copy in `onSuccess` and an entry in `exports`, never an `external` pattern, and `make smoke-pack` must not expect a JavaScript importer for them.

### Decision 3: a host with Tailwind that cannot compile the kernel's classes is documented as unsupported

Since kernel `0.8.0` the kernel's classes are Tailwind 4 class names, and the analysis above shows the prebuilt sheet cannot coexist with a Tailwind 3 host's own preflight and utilities in either position. A Tailwind 4 host that configures a prefix is in the same position: its build cannot generate the kernel's unprefixed classes, so it depends on the prebuilt sheet, and the sheet's preflight must rank below the host's base while its utilities must rank above it. The documentation says so in one sentence rather than offering a setup that cannot work.

## What each consumer does

The VS Code extension's webview is a host without Tailwind. It pins this package exactly, so it moves only when it bumps, and that bump adds one import of `@pipelex/mthds-ui/form-kernel.css` to the webview's entry. Its test that reads the kernel's sheet to check the shell defines every token the sheet uses stays valid unchanged. This is a follow-up owned by that repository and blocked on this item, filed as L-260925-226ec9.

The two Tailwind 4 host applications keep working through the upgrade with no change, because both already scan the kernel themselves and the statement naming the layer becomes a no-op. Each can then replace its `@source` path, its direct declaration of the kernel and its layer statement with the one import. Those simplifications are follow-ups owned by the hosts, with no urgency, filed as L-260925-235cfe and L-260925-43ced4.

The standalone bundle is unaffected. It ships the kernel's sheet through its own manifest in `scripts/standaloneCssFiles.mjs`, which lists `node_modules/@pipelex/mthds-form/dist/styles.css` directly. The alias that maps the wrapper stylesheet to that file exists only because `src/graph/react/index.ts` imports the wrapper, so it becomes dead once that import goes and is removed with it.

Storybook is a host without Tailwind and already imports `src/styles/form-kernel.css` explicitly in `.storybook/preview.ts`, so the stories keep the lane a host without Tailwind takes.

## Guards

- `src/styles/__tests__/formKernelLayer.test.ts` inverts its entry assertion: no React entry imports any kernel stylesheet, neither the raw specifier nor the wrapper, so injection cannot come back by accident. It keeps the assertions that the wrapper is layered and does not import `theme.css`.
- `make smoke-pack` gains a Tailwind 4 compile of a minimal host in its bare consumer, under npm and under pnpm, both required, since the pnpm virtual store is the layout the first `@source` candidate exists for. The minimal host's stylesheet is exactly the documented Tailwind 4 setup and nothing more: `tailwindcss`, `tw-animate-css`, the token mapping, and `@import "@pipelex/mthds-ui/tailwind.css"`, compiled against the installed tarball and the kernel it pulled in. The oracle is the kernel's own prebuilt `styles.css`: every selector in its `utilities` layer must appear in the minimal host's output. Finding one kernel-only class would prove only that the scan reached the package; comparing the whole set proves that the documented setup compiles what the kernel needs, semantic colour classes and animation classes included, and it follows the kernel from release to release with nothing written into the script. The check that every exported stylesheet has a JavaScript importer learns that the two host-imported stylesheets have none by design.
- The release carrying B is a breaking change under this repository's no-deprecation policy, recorded in the changelog with what each kind of host now loads.

## Review

Codex reviewed the draft adversarially on 2026-09-25. Accepted and folded in: `tailwind.css` alone does not make a Tailwind 4 host's setup complete, since the host's theme must map the tokens and it must load `tw-animate-css`, so the design now names the kernel's documented setup as the contract; a smoke check that finds one class proves only that the scan reached the package, so the oracle is now the kernel's whole prebuilt utility set; the pnpm run is a required gate rather than an option; the claim that B's failures are easy to see was overstated for Tailwind hosts and is now narrower; and the plan now also covers the README example that imports the kernel directly, the quick start's claim that the viewer handles styling, and the comment in `src/form/react/RunPanel.css` that describes the injection. Rejected: the objection that the changelog rule the plan cites does not exist. It is the workspace rule at `.claude/rules/changelog.md` above this repository, which loads whenever a changelog is edited.
